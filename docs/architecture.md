# Architecture

This document reflects what is actually implemented (Phase 1). It will
grow — not get rewritten from scratch — as each phase lands.

## Current shape

```
Browser (React/TS/Tailwind, :5173)
   |  fetch /api/*  (Vite dev-server proxy in dev)
   v
FastAPI backend (:8756)
   |  app/api/server.py — app factory, CORS, lifespan
   |  app/api/routes/health.py — GET /api/health
   v
app/core/config.py  — config/settings.json + PRATIKAI_* env vars, cached singleton
app/core/logging.py — console + rotating file handler (data/logs/pratikai.log)
   v
app/db/database.py  — SQLAlchemy engine/session (SQLite, foreign_keys=ON)
app/db/models.py    — full initial schema (14 tables, see README)
app/db/migrations/  — Alembic, autogenerated from models.py
   v
data/database/pratikai.db
```

Design intent for later phases, so this doesn't need restructuring:

- `app/core/config.py` centralizes all settings so a later `/api/settings`
  endpoint and Settings UI page can read/write the same source of truth.
- `Entity` (app/db/models.py) already carries every field the Phase 3
  Entity Manager needs (model, autonomy_level, computer_access,
  memory_enabled, face_path, voice_id) — Phase 3 adds the CRUD API and UI,
  not new columns.
- `Memory.entity_id` is nullable specifically to support the GLOBAL memory
  scope described in the spec (shared across entities) alongside per-entity
  private memory — enforced at the retrieval-layer in Phase 4, not by a
  separate table.
- The health check pattern (`app/api/routes/health.py`) is what
  `scripts/health_check.ps1` and later phases' STT/TTS/vision/avatar checks
  plug into — one aggregation point, not scattered ad-hoc pings.

## What is intentionally not built yet

No LLM calls, no entity logic, no memory retrieval, no speech, no vision,
no computer control. The frontend Sidebar shows every planned page with the
phase that implements it rather than linking to something that doesn't
work — see `frontend/src/components/Sidebar.tsx`.
